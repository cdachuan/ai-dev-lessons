# 反死记判别题模板

> 死记的人答得"完整漂亮但没切身体感"；真懂的人会带具体场景、踩过的坑、能反例。
> 判别题的核心：**逼出"体感"**，逼出"踩过坑"。

---

## 通用判别原则

1. **问"你"，不问"它"** — "你写过最长的 system prompt 是多少 token" 比 "system prompt 一般多长" 强 10 倍
2. **问具体数字** — 死记的人答不出 "你那个项目花了多少钱/多少时间"
3. **问反例** — "什么时候这个原则不成立" 比 "这个原则是什么" 强 10 倍
4. **问踩坑** — "你最近一次被坑是什么" 死记的人直接哑火
5. **问判准** — 不问"怎么做"问"凭什么决定这么做" — 决定背后是判断力，套路背后是死记

## 按主题分类的诊断题模板

### Prompt Engineering 主题

| # | 诊断题 | 死记答案特征 | 真懂答案特征 |
|---|--------|------------|------------|
| 1 | ReAct 跑偏了但 API 已经扣费，你会从哪三处加保险？ | 答"加 retry、加 validation" | 答具体到"我那次是这样加的：先 token 限速 + dry run + 用户确认" |
| 2 | 同一个 prompt 在 GPT-4o 跑得好，迁到 DeepSeek 立刻崩，三个最可能的原因？怎么验证？ | 答"模型不一样所以崩"（废话） | 答"中文指令遵循弱 / function call schema 严 / 长上下文衰减" 三选一，给验证步骤 |
| 3 | 写一个**自己用过的** JSON Schema 让模型返回结构化数据的例子，并说明**哪条 required 字段是为了防止模型犯懒** | 答 schema 教科书示例 | 答自己项目里那个 schema，并指出"我加了这个 enum 是因为模型总想偷懒给最常见的值" |

### Agent 架构 主题

| # | 诊断题 | 死记答案特征 | 真懂答案特征 |
|---|--------|------------|------------|
| 4 | Agent 调用工具失败重试 3 次都失败——继续重试/换工具/让用户选/直接放弃，怎么决定？判准是什么？ | 答"看情况" | 给出 2-3 个具体判据："看是不是网络抖动 / 看工具可替代性 / 看用户已经等了多久" |
| 5 | 你写过的最长的 system prompt 是多少 token？**为什么没拆？** 为什么没更长？ | 答"我没写过那么长的" | 答具体数字 + 拆/不拆的具体理由 |
| 6 | function calling 调通后你加的第一道防护是什么？（不是 API key 那一层） | 答"加 try-catch" | 答"参数白名单 / 危险操作确认 / 工具调用次数上限" 三选一，给项目实例 |

### RAG 主题

| # | 诊断题 | 死记答案特征 | 真懂答案特征 |
|---|--------|------------|------------|
| 7 | RAG 检索的 chunk 命中但答错——举一个**真实**例子（不构造），说你是怎么定位的 | 答"可能是 chunk 切错了" | 答"我那次是 1024 token 一切，但答案跨两个 chunk — 改成语义切分后好了" |
| 8 | embedding 召回率高但答案不对，三个最可能的瓶颈，**你怎么排序排查** | 答"调 embedding 模型" | 答"先看 query 改写 → 再看 rerank → 最后看 chunk 大小" 的排查顺序 + 为什么这个顺序 |

### Eval & Quality 主题

| # | 诊断题 | 死记答案特征 | 真懂答案特征 |
|---|--------|------------|------------|
| 9 | 不查文档，说出 eval set / golden set / benchmark 三个词各自的判别标准 | 三个混着答 | 一句话内各给一个明确边界："eval = 功能回归 / golden = 输出质量 / benchmark = 横向对比" |
| 10 | 100 字内解释为什么 fine-tuning 不是大多数 Agent 项目的正解，**举一个反例**说明什么时候 fine-tuning 才是正解 | 只答 fine-tuning 贵 | 答"更新慢、可控性差、贵" + 反例"风格统一/格式严格/领域术语翻译" |

| # | 诊断题 | 死记答案特征 | 真懂答案特征 |
|---|--------|------------|------------|
| 11 | 你最近一次被模型的"看起来对"骗到，是什么场景？**事后你怎么改的？** | 答不出 | 答具体故事 + 改的具体动作（加了什么检查/换什么评测） |

## 怎么用

### 给用户出题（推课时）

1. **先讲概念**（lesson 主体）
2. **再出 1 道诊断题**（挑该主题表里的 1-2 道，不超过 2 道）
3. **等用户答**（不评判，给思考空间）
4. **回看用户答案**——对照"死记特征"和"真懂特征"判别
5. **如果死记特征明显**：换个角度再问，或直接告知"这个答案我没看到体感，下次用你自己的项目例子重答"

### 课程设计时

- **每课必含 1 道诊断题**（位置在"概念讲完"和"动手前"之间）
- **诊断题不进 quiz 的"答案"区**（quiz 测事实，诊断题测体感，两码事）
- **诊断题不评分**（不是对错题，是深浅题）

### 升级路径

| 现象 | 诊断 | 处理 |
|------|------|------|
| 用户答得漂亮但没体感 | 死记 / 抄来的 / 没真做过 | 不责备，让他**用自己项目重答一遍** |
| 用户答不出但态度认真 | 知识盲区，缺实战 | 配对练：给个小项目逼他踩坑 |
| 用户答得带项目实例 | 真懂 | 进下一阶段，鼓励他给别的主题也出题 |
| 用户答得比模板还深 | 可以当 co-teacher | 邀请他贡献新题到这份文档 |

---

## 维护规则

- **新主题进来时**：照模板加 3-5 道题（覆盖"具体数字/反例/踩坑/判准"四类至少各一）
- **题被答了 10 次都没区分度**：换掉（"区分度"= 既能筛死记又不会被真懂的人答空）
- **不要写"标准答案"**：诊断题的价值在"激发思考"，不在"判分"

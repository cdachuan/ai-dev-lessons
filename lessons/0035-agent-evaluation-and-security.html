🩺 Agent 评估与安全

第 0035 课 · P5 实战篇 工程化课 · 预计 20 分钟

🎯 本课目标：给 34 课的 Agent 配一张「体检表」——固定一组测试问题，改代码前后各跑一遍，分数涨没涨一眼可见。再加安全四道闸，把「会算」的 Agent 变成「敢交给别人用」的 Agent。心法一句话：你不评估，就不知道自己的 Agent 到底行不行；你不设闸，就不敢把它交出去。

一、为什么 34 课之后马上要「评估」

34 课你给 Agent 装了核验卡口（口径声明 + 复算）。但「单个工具有卡口」不等于「整套 Agent 靠得住」——你怎么知道 Agent 在十种不同问法下都选对工具、都报对数？

📌 关键区别：34 课的核验是工具内部的自查；35 课的评估是站在 Agent 外面，拿一组固定问题当「考卷」，考它整体表现。前者防「算错」，后者防「这套 Agent 整体不行」。

二、评估三要素：考卷 = 问题 + 金标准 + 判分器

评估台（eval）不神秘，就是三样东西，全是纯代码、可复现——不接真 LLM 也能先把框架搭好、跑通：

  1. 固定测试集 EVAL_SET——一组写死的问题，覆盖不同考点：工具选对没、口径算对没、该拒绝时拒绝没。
  2. 金标准答案 golden——每题的标准答案，实跑 pandas 算出来的，不是拍的。
  3. 判分器 judge()——把 Agent 的实际输出和金标准比对，吐一个 PASS / FAIL。
# 评估集样例（完整版在 agent35_eval_demo.py，四题已实跑）
EVAL_SET = [
  {"question": "各品类已完成订单的销售额排名？",
   "expect_tool": "analyze",
   "golden": {"数码": 9932, "服饰": 9838, "食品": 6660, "家居": 6194}},
  {"question": "amount 的平均值是多少？",
   "expect_tool": "refuse",   # 正确行为 = 追问口径，不报数
   "golden": None},
]

三、四道评估题：一张「考卷」覆盖四个考点

题考点「裸奔」Agent 的表现
① 各品类已完成销售额排名口径正确性对（9932/9838/6660/6194）
② 这张表几行几列工具选择对（选了 data_profile，60 行 6 列）
③ 把退款也算进去，销售额？口径澄清错——不追问，直接报「已完成」口径的数
④ amount 平均值是多少失败场景错——直接报 661.2，没问「算全部还是已完成」
$ python agent35_eval_demo.py
通过 2/4 —— 裸奔 Agent 只过了 2 题。
这正是评估台的价值：改代码前后各跑一遍，分数涨没涨一眼可见。
⚠️ 一眼看懂「裸奔」死在哪：第③④题都是口径问题。裸奔 Agent 把「已完成」口径当成默认、算全表平均不追问——这两处正是 34 课「敢说不知道」的落空。评估台把这两个洞量化成了 FAIL，你才知道要补哪。

四、安全四道闸：敢交给别人用的前提

评估解决「对不对」，安全解决「会不会出事」。四道闸，从便宜到关键：

闸防什么做法
① API key 环境变量密钥泄露进代码 / gitkey 写进 .env 或环境变量，代码里用 os.environ.get() 读，永不写死在脚本里
② 输入边界恶意/畸形输入搞崩 Agent进 Agent 前的用户输入先校验长度、类型；工具参数照 30 课做校验
③ 危险操作确认Agent 删文件、改数据、发消息删/改/发送类工具，执行前要求人工确认（原数据只读，正是 34 课定下的）
④ 成本记录调用失控烧钱每次调 LLM 记 token 数 / 费用，设单次上限，超了就停
 
# ① API key：永远这么读，不写死
import os
api_key = os.environ.get("DEEPSEEK_API_KEY")
if not api_key:
    raise SystemExit("未找到 DEEPSEEK_API_KEY，请在环境变量里配置")

# ④ 成本：每轮累计 token，超上限就停
if total_tokens > MAX_TOKENS:
    return "已达本轮 token 上限，请缩小问题范围或提高预算"
📌 原数据只读（接 34 课）：安全闸③和 34 课「原数据物理只读」是同一条线——Agent 对原数据永远只读，任何改动都是「衍生品」，改决策=删下游重跑。这样即使 Agent 想作妖，也动不了你的底账。

五、实操任务（15 分钟）

  1. 跑 python agent35_eval_demo.py，看「裸奔」Agent 的 2/4 分，对着三、四两节的表格，确认它死在③④两题
  2. 改代码让分数涨：给 analyze 加一个 include_refund=False 参数（34 课挑战题正好接上）——第③题就能「同时给两个口径的数」；给 Agent 加「口径不清先反问」的规则，第④题就能转 PASS
  3. 把改完的 Agent 重新跑评估台，亲眼看到分数从 2/4 涨到 3/4 甚至 4/4——这就是「评估驱动开发」的完整闭环
🎯 本课核心结论：评估台是一张可反复跑的考卷，它把「Agent 行不行」从玄学变成数字。你以后每改一次 Agent（换工具、改 prompt、换模型），第一件事就是重跑评估台看分数——涨了说明改对了，掉了说明改坏了。这是 43 课毕业作品「可演示」的底气来源。

本课学了什么

  • ✅ 评估三要素：固定测试集 + 金标准答案（实跑算出）+ 判分器，纯代码可复现
  • ✅ 四道评估题：覆盖「工具选择 / 口径正确性 / 口径澄清 / 失败场景」四个考点
  • ✅ 评估驱动开发：改代码前后各跑一遍，分数涨跌=改对改错
  • ✅ 安全四道闸：API key 环境变量、输入边界、危险操作确认、成本记录

你调了一版 Agent，想把「各品类已完成销售额」的正确答案从 4/4 稳到 4/4，但心里没底它改好没有。下面哪个做法最能给你确定的答案？

  1. 手动多问它几遍，凭感觉判断稳不稳
  2. 写死一组测试问题+金标准答案，改一次跑一次，看 PASS 数量
  3. 换一个更贵的大模型重试
  4. 把工具的 description 写得更长更详细

小测答案：B。写死测试集 + 金标准 + 判分器，改一次跑一次看 PASS 数——这正是本课评估台的意义：把「稳不稳」从感觉变成可复现的数字。A 错：手动多问凭感觉，同一问法你可能问出不同结果，更别说换种问法就露馅，没有可比性。C 错：换贵模型是赌「更强的模型更稳」，但没有评估台，你根本不知道它到底稳没稳——贵模型也可能在某个口径上同样翻车，只是翻得更自信。D 错：改 description 是 30 课的「工具决策」优化，它解决「选错工具」，解决不了「算错数」「该拒绝没拒绝」——那些要靠评估台暴露出来。这题的教训：「确定」不是问出来的，是拿固定考卷反复跑出来的。以后任何人（包括你自己）说「这版 Agent 稳了」，第一反应都该是：评估分数多少？

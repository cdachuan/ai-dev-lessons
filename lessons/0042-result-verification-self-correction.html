🔍 结果验证与自我修正

第 0042 课 · P6 真实世界 + 可靠性 工程课 · 预计 15 分钟

🎯 本课目标：让 Agent 学会「自己检查自己的答案」——SQL/Python 结果出来后，先过一遍验证，空结果或异常值自动重试，而不是自信地把错答案报给你。这是从「能跑」到「可信」的关键一步。

一、为什么需要结果验证？

你 37 课的 capstone_kit 已经有了 verify 工具——这是核验思想的起点。但在真实场景里，Agent 可能犯的错误远不止「数字算错」：

错误类型真实案例后果
空结果 筛选条件写错，status == "已完成" 写成 status == "完成" Agent 报告「该品类销售额为 0」，你信了
异常值 一笔退款金额是负数 -5000，其他订单都是正数 总和被拉低，结论偏差很大
口径不一致 这次算了含退款的总额，下次又不算 给领导的数字前后矛盾
代码执行失败 列名拼错、数据类型不匹配 Agent 用空值硬算，得到荒谬结果
⚠️ 最危险的情况：Agent 算出一个看起来「合理」的错误答案——比如某品类销售额是 0（实际是筛选条件写错了），你没有验证就信了。没有验证的分析，不如不做。

二、verify 核验卡口：你已经会的东西

34 课你亲手做的 verify 工具，核心思想是：用独立写法的代码路径复算同一个数。

# 主算法：用 groupby 算各品类销售额
df.groupby("品类")["金额"].sum()

# verify：用布尔索引 + sum 复算（不同的写法）
df[df["状态"] == "已完成"].query("品类=='数码'")["金额"].sum()

两个结果应该一致——如果不一致，说明其中一条路径有 bug。

📌 42 课的增量：34 课的 verify 是「手动调用一次」。现在我们要把它自动化——Agent 出结论前，代码自动检查结果是否合理，不合理就触发重试或修正。

三、三种可落地的验证策略

策略 1：空结果检测

最简单也最常见——算出来的结果是空的、0、或者 None。

# 空结果检测：group_sum 返回空字典时
def _is_empty_result(result):
    """检查工具返回结果是否为空"""
    if not result:
        return True
    data = result.get("结果", {})
    if isinstance(data, dict) and len(data) == 0:
        return True
    if isinstance(data, (int, float)) and data == 0:
        return True
    return False

检测到空结果后，Agent 应该做什么？

  1. 先检查筛选条件——是不是 filter_status 写错了？比如用户问「已完成订单的销售额」，Agent 却写了 status == "完成"（少了个「已」字）。
  2. 检查列名——拼写对不对？大小写对不对？
  3. 如果确实没有数据——如实告知用户，不要编一个 0 出来。

策略 2：异常值检测

结果不是空的，但数字看起来不对劲。

# 异常值检测：金额出现负数、或单笔金额远超均值
def _has_anomaly(result):
    """检查数值结果是否有明显异常"""
    data = result.get("结果", {})
    if not isinstance(data, dict):
        return False
    values = list(data.values())
    if not values:
        return False
    # 检查1：是否有负数（金额通常不该为负）
    if any(v < 0 for v in values):
        return True
    # 检查2：是否有极端值（超过均值 10 倍）
    mean_val = sum(values) / len(values)
    if mean_val > 0 and any(v > mean_val * 10 for v in values):
        return True
    return False
📌 什么时候该报警？不是所有「看起来奇怪」的数都是错的。比如退款金额是负数——这恰恰是正确的。关键是：你要知道数据的业务含义，才能判断什么是「异常」。

策略 3：口径一致性检查

同一个问题，两次问得到不同数字——口径可能变了。

# 口径检查：两次 group_sum 的 filter_status 是否一致
def _check_consistency(result, expected_status):
    """检查实际使用的口径是否与预期一致"""
    actual_status = result.get("filter_status")
    if actual_status != expected_status:
        return False, {
            "expected": expected_status,
            "actual": actual_status
        }
    return True, None

四、在 Agent 循环中嵌入验证

把上面三种检测串起来，嵌入到 ReAct 循环里：

用户提问
   │
   ▼
┌──────────────────────────────────────┐
│  ReAct 循环（每步执行工具后）         │
│                                      │
│  1. 执行工具 → 得到 result           │
│  2. 检查 _is_empty_result(result)    │
│     → 空？提示 Agent 修正条件重试    │
│  3. 检查 _has_anomaly(result)        │
│     → 异常？提示 Agent 检查数据      │
│  4. 检查 _check_consistency(result)  │
│     → 口径不对？提示 Agent 重算      │
│  5. 通过 → 继续下一步                │
└──────────────────────────────────────┘
   │
   ▼
出结论前调 verify（独立复算）
   │
   ▼
最终答案

代码实现：包装工具调用

# 在 core.py 里，执行工具后加一层验证
def _execute_and_validate(tool_name, args, tool_func):
    """执行工具并自动验证结果"""
    result = tool_func(**args)

    # 空结果检测
    if _is_empty_result(result):
        result["_warning"] = (
            "⚠️ 结果为空，请检查：筛选条件是否正确？列名是否拼写正确？"
        )

    # 异常值检测
    if _has_anomaly(result):
        result["_warning"] = (
            "⚠️ 结果包含异常值，请确认：数据是否需要清洗？"
        )

    return result
💡 关键设计：验证结果通过 _warning 字段附加到返回值里，不会中断 Agent 循环——Agent 会看到警告，然后自己决定是否重试或修正。这是「软约束」而非「硬中断」。

五、动手任务：给分组统计工具加自检

基于你 37 课的 capstone_kit，给 group_sum 工具加一个「结果为空/数量为 0」的自检：

  1. 打开 agent/tools.py，找到 group_sum 函数。
  2. 在返回结果之前，加一个空结果检查： 
    # 在 return 之前加
result = {"结果": {k: int(v) for k, v in s.items()}}
if len(result["结果"]) == 0:
    result["_warning"] = "结果为空：筛选条件下没有匹配的数据"
return result
  3. 同样给 group_count 加上相同的检查。
  4. 在 tests/eval.py 里加一个测试：用不存在的筛选条件调 group_sum，验证返回结果包含 _warning。
  5. 跑 python main.py --selftest，确认所有测试通过。
📌 为什么从空结果开始？空结果是最常见、最容易检测、也最容易被忽略的错误。一个「销售额为 0」的空结果如果没被发现，后面所有分析都是废的。先堵住最大的漏洞。

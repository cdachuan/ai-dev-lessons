🤖 Agent + 数据分析（多工具协作）

第 0034 课 · P5 实战篇 交叉核心课 · 预计 25 分钟

🎯 本课目标：亲手搭一个「带核验卡口」的数分 Agent——它自己读数据、算指标、画图，但每一步都把「口径」写进产出、留痕可复算。核心心法一句话：「想」和「算」分离，核验是内置步骤，不是事后想起来的可选后缀。

一、从 pandasai 到自建 Agent：差的是一道卡口

32 课我们下了结论：pandasai 出局的真正原因是架构——它没有地方放「核验」这道卡口，LLM 生成代码就直接执行、直接报数。你会 pandas、在意口径，需要的不是「翻译层」，是一个你自己能插手的 Agent。

维度pandasai（32 课）自建数分 Agent（本课）
「想」大模型翻译成代码大模型选工具 + 定参数
「算」本机执行生成代码你写的 pandas 工具
核验卡口没有口径声明 + 复算，内置
中间产物不可见profile 卡片 / 口径 / 结果留痕

底层的「想算分离」其实和 pandasai 一模一样——真正让两者分道扬镳的，就是那一行「口径声明」和一个「复算」动作。本课就做这两件事。

二、Agent 怎么「看懂」一张表：感知三层

Agent 不能把 60 行数据全塞进上下文（又贵又散）。正确姿势是先画像、再看数据，分三层：

层谁来做产出什么
① 机械画像代码（自动）shape / 列名 / 类型 / 缺失 / 前几行，压成几百字符的「卡片」
② 语义解读LLM（猜）+ 你审猜各列是啥（主键？金额？日期？）、口径疑似问题
③ 人为补充你（数据字典）列的真实含义 / 口径 / 坑，一次写长期复用
📌 分工铁律：画像自动做、语义机器猜人审、口径和坑永远人说了算。本课落地第①层（机械画像），② 体验一下，③ 留到 43 课做成数据字典 YAML——那会是你作品的亮点（人对 AI 的知识输入工程化）。

三、最小骨架：三个工具 + 核验卡口（已实跑验证）

演示数据仍是 orders_60.csv（60 行，4 个品类，46 单已完成 / 14 单已退款），在 D:\学习\AI\工具实操\。ReAct 主循环复用 28 课骨架，一行不改——本课新增的是下面三个工具函数。

import pandas as pd, json

# ① 感知工具：机械画像 —— 60 行压成一张几百字符的卡片（实测 717 字符）
def data_profile(df):
    card = {
        "shape": list(df.shape),
        "columns": list(df.columns),
        "dtypes": {c: str(df[c].dtype) for c in df.columns},
        "missing": df.isna().sum().to_dict(),
        "status": df["status"].value_counts().to_dict(),
        "head": df.head(3).to_dict("records"),
    }
    return json.dumps(card, ensure_ascii=False)

# ② 分析工具：默认剔除退款，并把「口径」写进返回值（核验卡口在此）
def analyze(df, by, metric, agg):
    done = df[df["status"] == "已完成"]        # 口径：只看已完成订单
    result = done.groupby(by)[metric].agg(agg).sort_values(ascending=False)
    return {
        "口径": "已剔除 status='已退款' 的订单",
        "结果": result.to_dict(),
    }
# ③ 图表工具：复用 33 课 pyecharts，落盘成 HTML 文件
from pyecharts.charts import Bar
from pyecharts import options as opts

def make_bar(df, by="category", metric="amount"):
    done = df[df["status"] == "已完成"]
    s = done.groupby(by)[metric].sum().sort_values(ascending=False)
    (Bar().add_xaxis(s.index.tolist())
          .add_yaxis("销售额(元)", s.values.tolist())
          .set_global_opts(title_opts=opts.TitleOpts(title="各品类销售额(剔除退款)"))
     ).render("品类销售额.html")
    return "已生成 品类销售额.html，浏览器打开可交互"

三个工具的 TOOL_REGISTRY 和 description，照 30 课的四条铁律写——尤其给 analyze 写清「何时该用、何时不该用」：

"analyze": {
    "func": analyze,
    "description": "对数据做分组聚合（sum/count/mean），默认剔除已退款订单并返回口径声明。"
                 "用在你已经知道要按哪列分组、算哪个指标时。"
                 "不要用它探索数据长什么样（先用 data_profile 画像）。"
}
🎯 实测结果（本节代码真实跑出来的）：各品类「已完成」销售额 = 数码 9932 / 服饰 9838 / 食品 6660 / 家居 6194，合计 32624；若不过滤退款直接算则是 39670。同一张表，口径差一个条件，数字差 7000 多——这就是为什么口径必须跟着结果一起返回。

四、核验卡口：本课的灵魂

回顾 32 课结尾那个探讨，我们定了三大产品级要求，本课先做进前两条：

  1. 核验是内置步骤——analyze 的返回值自带口径字段，不是「跑完再口头解释」。Agent 报数必带口径，这是硬约束。
  2. 中间产物可见——profile 卡片、口径、结果全部留痕（返回 JSON），图表落盘成 HTML。任何一步都能回溯。
  3. 敢说不知道——口径不清就拒绝回答。这条要等 35 课「评估与安全」和 43 课数据字典接上才完整。

再加一道人的卡口——复算，10 秒钟的事：

# Agent 报了「数码 9932」，你自己手写一遍对账
done = df[df["status"] == "已完成"]
print(done.groupby("category")["amount"].sum())
📌 反直觉的提醒：自建 Agent 的兜底逻辑全是自己写的，漏了验证反而会「错得更自信」——因为它看起来比 pandasai 更「专业」。核验卡口不是锦上添花，是保命绳。

五、实操任务（15 分钟）

  1. 把第三节三个工具函数抄进一个 agent34.py，跑一遍 data_profile，看画像卡片长什么样（注意它比 60 行数据短多少）
  2. 跑 analyze(df, "category", "amount", "sum")，确认返回值里带口径字段，数字对上「数码 9932」
  3. 挑战：给 analyze 加一个参数 exclude_refund=True，改成「口径可切换」——领导问退款时你能同时给出两个数字

小测答案：C。把「口径声明 + 复算」做成 analyze 的默认输出是唯一根治——这课的整条主线就是「核验是内置步骤，不是可选后缀」：口径字段跟着结果每次自动返回，领导的问题在你开口前就被回答了，复算卡口也让错误在源头被拦下。A 错：换更贵的模型提升的是「想」的命中率，不是「核验」——同样可能算错，只是错得更流利。B 错：工具更多 ≠ 更可靠，反而可能让 Agent 更纠结（30 课：4-8 个是合理区间）。D 错：把口径变成「可选、按需解释」，恰恰是本课要消灭的坏习惯——它让核验退化成事后补救，而事后往往已经来不及。这题的教训：让 AI 报的数「可信」，靠的不是更强的模型，是把它设计成「不报口径就报不了数」。

第一步：四个数据工具

def load_data():
    """读数据，返回表结构画像 + 前3行（感知层雏形）"""
    df = pd.read_csv(DATA)
    return {"行数": len(df), "列": list(df.columns),
            "状态取值": df["status"].unique().tolist(),
            "前3行": df.head(3).to_dict("records")}

def groupby_sum(group_col, value_col, filter_status=None):
    """分组求和，filter_status 可过滤状态（口径开关）"""
    df = pd.read_csv(DATA)
    if filter_status: df = df[df["status"] == filter_status]
    s = df.groupby(group_col)[value_col].sum().sort_values(ascending=False)
    return {k: int(v) for k, v in s.items()}

def nunique(col):
    """去重计数（31课小测的机器版）"""
    return int(pd.read_csv(DATA)[col].nunique())

def verify(claim, independent_code):
    """【核验卡口】用独立路径复算 claim"""
    df = pd.read_csv(DATA)
    real = eval(independent_code, {"__builtins__": {}}, {"df": df, "pd": pd})
    return {"claim": claim, "独立复算": real}
⚠️ 口径开关是灵魂：groupby_sum 的 filter_status 参数，就是 31 课「算销售额要不要排除退款」的机器版。AI 必须自己判断传不传 '已完成'——传错，第一名就换人。

第二步：为什么「核验」不能用同一段代码

核验的关键陷阱：如果复算用同一段代码，只会重复同一个错误。必须用独立的算法路径：

原始计算独立复算（verify 里）
groupby_sum('category','amount','已完成')df[df.status=='已完成'].groupby('category').amount.sum()

两种写法不同，但都指向同一口径。只有两条独立路径得出同一个数，结论才可信。

第三步：真实执行记录（本课实跑）

下面是本课实际跑通的完整 trace（问题：「各品类销售额（剔除退款）」）：

[step 1] → load_data()
[step 2] → groupby_sum(过滤'已完成')
[step 3] → verify(独立复算)
✓ 独立复算结果与原结果一致，验证通过
→ 数码 9932（最高），家居 6194（最低），已剔除退款

看到三个关键点

  1. AI 自己先 load_data——没被催，是 system prompt 里的铁律驱动的
  2. AI 自己过滤了「已完成」——它主动意识到要排除退款单（口径意识）
  3. AI 出结论前调了 verify——核验卡口生效，且复算用的独立写法

第四步：实测两个口径的差异（本课教学点）

同一个数据，过滤与否，第一名直接换：

口径第一名第二名
不过滤退款服饰 13424数码 10519
过滤「已完成」数码 9932服饰 9838
💡 这就是为什么核验卡口不是可选项：如果 AI 忘了过滤，它会自信地告诉你「服饰第一」。核验让「口径错误」在出结论前被逮住，而不是等你拿去汇报才发现。

🤔 小测：为什么 verify 的复算不能用「跟 groupby_sum 一样的代码」？
🔴 安全红线（提前预告 35 课）：本课 verify 用了 eval() 执行 AI 生成的代码——仅限演示，且限制了 __builtins__。生产环境绝不允许直接 eval AI 代码，必须放沙箱。35 课专门讲这个。

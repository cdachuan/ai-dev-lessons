🔌 工具生态：Function Calling 进阶与 MCP

第 0023 课 · 进阶篇 概念课

🎯 本课目标：理解工具调用的三层进化——从单次 Function Calling，到多工具编排，再到 MCP 标准化共享。学完你能说清「什么时候用什么」。

回顾：Function Calling 是什么

第 10 课你学过 Function Calling——让 AI 调用你写好的函数。核心流程是这样的：

# 你定义一个函数
def query_meter(meter_id, date):
    # 查数据库，返回日电量
    return db.query(meter_id, date)

# 告诉 AI 这个函数怎么用
tools = [{
    "name": "query_meter",
    "description": "查询某电表某日的电量数据",
    "parameters": { "meter_id": "string", "date": "string" }
}]

# AI 看到用户问"查一下T07台区8月1日电量"，自己决定调用这个函数

关键点：AI 不是自己写查询代码，而是从你提供的工具列表里选一个调用。你负责写函数和定义，AI 负责决定什么时候用、用什么参数。

📌 第 10 课的核心：一个工具，一次调用。AI 看到一个问题，选一个函数，传参数，拿结果，回答用户。

进阶：从「一个工具」到「工具列表」

真实场景中，一个智能体不可能只有一个工具。你可能需要：查电表、查台区、算波动、画图、发邮件……把这些函数全部注册成工具列表，AI 自己选该调哪个。

tools = [
    {"name": "query_meter",     "description": "查电表日电量"},
    {"name": "query_taigu",    "description": "查台区信息"},
    {"name": "calc_fluctuation", "description": "算用电波动幅度"},
    {"name": "draw_chart",     "description": "画柱状图"},
    {"name": "send_email",     "description": "发邮件通知"},
]

# 用户说："查T07台区8月波动，画个图，发给张工"
# AI 自动按顺序调用：query_taigu → calc_fluctuation → draw_chart → send_email

这就是工具注册——你把一堆函数的「说明书」交给 AI，AI 根据用户需求自己决定调哪个、什么顺序调。你不用写 if-else 去判断用户想干嘛，AI 自己路由。

用你的 Coze 经验理解

你在大赛项目里用过 Coze（扣子），其实你已经接触过这套东西了，只是叫法不同：

Coze 里的概念对应的技术概念你做过的事
插件（Plugin）Function Calling 的一个工具在 Coze 里加个天气插件、搜索插件
工作流（Workflow）多个工具串联编排把「搜索→提取→总结」串成一条线
Bot / Agent带工具列表的智能体给 Bot 配上插件，让它自己决定调用
💡 一句话打通：Coze 插件 = Function Calling 工具；Coze 工作流 = 多个 Function Calling 串起来；Coze Bot = 注册了工具列表的 Agent。你在 Coze 上拖拽的东西，底层就是这套机制。

MCP：工具的「USB 接口」

现在问题来了——你在 Coze 里配好的插件，换到另一个 AI 平台还能用吗？在 OpenAI 的 Function Calling 里写的工具，换到 Claude 还能直接用吗？

以前不能。每个 AI 平台的工具格式不一样，换个平台就得重写一遍。MCP（Model Context Protocol）就是来解决这个问题的。

🔌 MCP 的 USB 类比：USB 出现之前，鼠标有鼠标的接口，键盘有键盘的接口，打印机又是另一种接口，每个设备单独写驱动。USB 出现之后，不管什么设备，插上就能用。MCP 之于 AI 工具，就像 USB 之于硬件设备——不管什么 AI（Claude、GPT、本地模型），插上同一个 MCP 工具就能用，不用每个 AI 单独写适配。

具体来说，MCP 做了这件事：定义了一套标准协议，规定工具怎么描述自己、怎么被调用、怎么返回结果。工具开发者按 MCP 标准写一遍，所有支持 MCP 的 AI 都能直接调用。

对比传统 Function CallingMCP
工具写几遍每个 AI 平台写一遍写一遍，所有 AI 都能用
谁定格式各 AI 平台自己定（OpenAI 一套，Claude 一套）统一标准，谁都遵守
换 AI 平台工具代码大概率要改工具不用改，直接接入
共享给别人得连代码一起给，对方还得适配给一个 MCP 地址，对方直接连

你工作中的 MCP 实例

你的知识问答智能体项目里，已经用了 MCP 封装。回忆一下那个架构：

  • 文件处理 MCP——读取 PDF、Word、Excel，提取文字内容。不管哪个智能体要用，调这个 MCP 就行，不用每个项目自己写一套文件解析逻辑。
  • 知识库检索 MCP——接收一个问题，去向量库里搜相关段落，返回结果。这个能力也是封装好的，任何智能体都能调。

如果你不用 MCP，而是每个智能体各自写一遍文件解析和知识检索——3 个智能体就是 3 份代码，改一个 bug 要改 3 个地方。用了 MCP，改一处，3 个智能体同时受益。这就是标准化的价值。

什么时候用什么

这三层不是互相替代，而是不同场景用不同的层：

场景用什么举例
单次调用，一个工具就够Function Calling用户问天气 → 调一次天气 API → 回答
多个工具要按逻辑编排工作流 / Agent查数据 → 算指标 → 画图 → 发邮件
多个智能体共享同一个能力MCP3 个智能体都要查电能量，封装成一个 MCP 工具共享
💡 记住这个递进关系：Function Calling（单工具）→ 工作流/Agent（多工具编排）→ MCP（标准化共享）。不是越高级越好，而是看你的场景需要哪一层。一个工具能搞定的事，别上 MCP。

🤔 小测

你的团队有 3 个智能体都要用到「查询电能量数据」这个能力。怎么做最合理？

  1. 每个智能体各自写一份查询代码
  2. 把查询能力封装成一个 MCP 工具，3 个智能体都调用同一份
  3. 用 Function Calling，每次需要时让 AI 生成查询代码
  4. 手动查询后把结果复制给每个智能体

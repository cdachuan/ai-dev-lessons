💰 成本与延迟：分档调用 / 缓存 / 批处理

第 0055 课 · 选修线三 Agent深水区 · 预计 20 分钟

🎯 本课目标：把 38 课那句「便宜模型+好架构 > 强模型+裸奔」落成工程手段：分档调用、缓存、批处理三招，外加延迟预算的意识。

一、分档调用：不是所有步都配得起强模型

Agent 的一趟任务里，各步难度天差地别：

步骤难度配置档位
理解用户问题、拆解任务高（语义判断）强模型
选工具、定参数中中档
SQL 生成、代码生成中高中档+校验
结果摘要、格式转换低（模板化）便宜模型甚至纯代码
算术、聚合、排序零不调模型——代码写死

最便宜的一档永远是「不调模型」：能用 pandas 算的绝不让模型算，能用正则抽的绝不调接口。38 课划的线在这里变成省钱的艺术。

二、缓存：同一问题第二次就该是免费的

三层缓存，从粗到细：

  • 结果缓存：问题归一化后（去停用词/同义词映射）哈希存答案。用户问「各月销售额趋势」和「月度GMV走势」应该命中同一条
  • 数据缓存：工具层的中间结果（清洗后的 DataFrame）落盘复用，别每次重洗 54 万行
  • 提示缓存：系统提示+schema 是固定前缀，选支持 prompt caching 的服务，前缀部分按折扣计费
📌 缓存的坑：数据更新后缓存必须失效——给缓存键加「数据版本号」（如数据文件 hash 前 8 位）。脏缓存比没有缓存糟糕得多，这又是 42 课 verify 思想的变体。

三、批处理与并发：结构性省时省钱

  • 批处理 API：离线任务（如批量评估 15 题）用 batch 接口，通常半价，只要不急
  • 并发评估：评估集题目互相独立，并发跑，总时长 = 最慢一题而非总和
  • 合并调用：5 个独立小问题合成 1 次调用批量问，省 4 次固定开销——但别合并有依赖的问题

四、延迟预算：用户体感表

等待时长用户体感设计对策
< 1s即时缓存命中、纯代码路径
1-5s可等单次模型调用
5-30s需要反馈流式输出/进度提示（「正在查询数据…」）
> 30s流失区异步任务+完成通知，或拆阶段

你的 Streamlit 界面里 st.spinner("Agent 分析中…") 就是最朴素的延迟对策——不能缩短等待时，至少让等待可见。

动手任务（20 分钟）

  1. 给你的 MVP 记账：在 core.py 加一个 token 计数器，跑 3 个评估问题，看每题花在哪一步。
  2. 实现结果缓存：问题 hash → 答案，跑同一问题两次对比延迟。
  3. 把评估集改成并发执行，测总时长变化。
🎯 本课核心结论：成本优化的优先级：不调模型 > 调便宜模型 > 缓存 > 减少步数 > 换强模型。延迟优化优先级：缓存 > 流式反馈 > 并发 > 异步。两张清单贴在工位上，比什么优化技巧都值钱。

本课学了什么

  • ✅ 分档调用：按步骤难度配模型，最便宜档是「不调模型」
  • ✅ 三层缓存：结果/数据/提示，缓存键带数据版本防脏
  • ✅ 批处理：离线评估半价，独立任务并发跑
  • ✅ 延迟预算：1s/5s/30s 三条体感线，各有对策

🤔 小测

Agent 每次回答前都重新清洗一遍 54 万行 CSV（约 20 秒），最优改造是？

  1. 换更快的电脑
  2. 数据缓存：清洗结果落盘（带数据版本号的键），第二次起直接加载
  3. 让模型写更快的清洗代码
  4. 改用流式输出让用户等得不无聊

小测答案：B。重复的确定性计算结果必须缓存——这是零风险零成本的结构性优化（注意键里带数据版本号防脏缓存）。
A 错：硬件是逃避架构问题的昂贵解法，换台慢的还得再还债。
C 错：清洗是确定性代码，快慢与模型无关——这是「能代码解决的不调模型」的反面教材。
D 错：流式输出只是让等待「看起来」短，20 秒还是 20 秒；缓存才能让它真的变 0.1 秒。先缓存，再谈体验补偿。

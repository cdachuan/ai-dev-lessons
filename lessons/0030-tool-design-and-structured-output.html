🛠️ 工具设计与结构化输出

第 0030 课 · P5 实战篇 工程化课

🎯 本课目标：把 28-29 课「能跑起来」的 Agent，升级成「稳定可控」的工具集。三个工程武器：参数校验（AI 传错参数就拦下来） + 统一返回格式（成功失败一眼分清） + 写好 description（AI 知道何时该调、不会乱调）。这是「能跑」和「能用」的分水岭。

从「能跑」到「能跑稳」：3 个新问题

29 课你的 Agent 已经能调真实 HTTP API 了。试着想想——真把它交给同事用，会遇到什么：

  1. AI 传错参数：用户问「查 T07 台区电量」，AI 调 query_taigu_kwh(taigu_id=7, date="今天")——taigu_id 应该是 "T07" 字符串不是数字 7，date 应该是 "2026-08-27" 不是「今天」。你的函数要么报错崩溃，要么静默返回错误数据。
  2. 返回格式混乱：有时候返回字典，有时候返回字符串，有时候返回 None。AI 拿到的数据「形状不固定」，下一次推理就抓瞎。
  3. AI 该调不调、不该调乱调：用户问「今天星期几」，AI 也想调 query_taigu_kwh；用户问「T07 电量」，AI 调了 query_line_loss_rate。根因是 description 没说清「什么时候该用我」。
📌 本课三个工程武器：
  • 武器 1：参数校验——AI 传错参数，工具直接告诉它「错了，重传」
  • 武器 2：统一返回格式——永远 {"ok": True/False, ...}，AI 不用猜
  • 武器 3：好的 description——写清「何时用、何时不用」，AI 选对工具

武器 1：参数校验——AI 传错就拦下来

工具函数最常见的「崩溃源」是 AI 传了不符合要求的参数。解决方法很直接：函数开头先校验，不符合要求就返回错误结构，不抛异常——因为异常会打断 Agent 的推理流，错误结构反而能让 AI 看到「参数不对，我重传」。

# tools_validated.py —— 加了参数校验的工具
import re
from datetime import datetime

def query_taigu_kwh(taigu_id, date):
    """查询指定台区在某一天的电量（kWh）"""

    # 校验 1：台区编号必须是 T 加 2-3 位数字
    if not re.match(r"^T\d{2,3}$", taigu_id):
        return {
            "ok": False,
            "error": f"taigu_id 格式错：'{taigu_id}'，应该是 T 加 2-3 位数字，如 T07、T102"
        }

    # 校验 2：日期必须是 YYYY-MM-DD
    try:
        datetime.strptime(date, "%Y-%m-%d")
    except ValueError:
        return {
            "ok": False,
            "ok": False,
            "error": f"date 格式错：'{date}'，应该是 YYYY-MM-DD，如 2026-08-27"
        }

    # 校验通过，执行真正的查询
    data = db_query(f"SELECT kwh FROM meter WHERE taigu='{taigu_id}' AND day='{date}'")
    if not data:
        return {"ok": False, "error": f"没找到 {taigu_id} 在 {date} 的数据"}

    return {"ok": True, "data": {"taigu_id": taigu_id, "date": date, "kwh": data[0]}}
💡 关键设计：参数错误时不抛异常，而是返回错误结构。原因是：异常会中断 Agent 的 ReAct 循环，错误结构却能让 AI 看到「我参数传错了，我重传」。Agent 拿到 {"ok": False, "error": "..."}，会自动修正参数重试一次。这是 AI Agent 工程化的核心模式——把错误变成可读信息。

武器 2：统一返回格式——永远 {"ok": ..., ...}

每个工具函数，无论成功失败，返回值永远是同一个「壳」：

# 成功
{
  "ok": True,
  "data": {/* 业务数据 */}
}

# 失败（参数错 / 找不到 / 内部异常）
{
  "ok": False,
  "error": "人类可读的错误说明"
}

这给 Agent 带来两个好处：

  1. 判断简单：AI 永远先看 ok 字段，是 True 就读 data，是 False 就读 error 决定怎么办
  2. 写代码简单：你在 ReAct 主循环里，不用给每个工具写不同的异常处理，统一调 TOOL_REGISTRY[name](**args)，try/except 只兜底 Python 异常
⚠️ 反例：不要让有的工具返回字典、有的返回列表、有的返回字符串、有的返回 None。「返回格式不统一」是 AI Agent 工程化最大的坑之一——AI 下次推理要靠记忆分辨每个工具的返回类型，一次新会话就忘光。统一 {"ok": ..., ...} 之后，AI 不用记。

武器 3：好的 description——决定 AI 会不会选对工具

description 是 AI 决定「用不用这个工具」「什么时候用」的唯一依据。AI 看不到你的函数名（除了关键词匹配），看不到函数内部代码，只看 description。写 description 有 4 条铁律：

铁律反例 ❌正例 ✅
1. 写明输入是什么 「查电量」 「查询指定台区在某一天的电量（kWh）」
2. 写明输出是什么 「返回数据」 「返回 {taigu_id, date, kwh}，kwh 是数字」
3. 写明何时该用 「查电量工具」 「当用户问某台区某天的电量时使用。不要用于查询线损、对比多个台区」
4. 写明何时不该用 （没说） 「如果用户只问'哪个台区用电高'，请用 compare_taigus」 
# 工具说明书（一个完整的、好 description 的例子）
{
  "type": "function",
  "function": {
    "name": "query_taigu_kwh",
    "description": "查询某个台区在某一天的电量（kWh）。当用户问【单个台区某天/某段时间的用电量】时使用。返回 {taigu_id, date, kwh}。不要用于：(1) 多个台区对比（用 compare_taigus），(2) 查询线损率（用 query_line_loss_rate），(3) 算变化百分比（用 calculate_pct_change）。",
    "parameters": {
      "type": "object",
      "properties": {
        "taigu_id": {
          "type": "string",
          "description": "台区编号，格式 T 加 2-3 位数字，如 T07、T102",
          "pattern": "^T\\d{2,3}$"
        },
        "date": {
          "type": "string",
          "description": "日期，格式 YYYY-MM-DD，如 2026-08-27",
          "pattern": "^\\d{4}-\\d{2}-\\d{2}$"
        }
      },
      "required": ["taigu_id", "date"]
    }
  }
}
📌 JSON Schema 里的 pattern：上面 taigu_id 和 date 都加了正则约束。DeepSeek / GPT 这类大模型会尽量遵守正则，但不能完全依赖——这就是为什么函数内部还要再做一次参数校验。Schema 是「软约束」，函数校验是「硬约束」，两者都要有。

三个武器一起用：完整工具模板

# tools.py —— 标准工具模板：校验 + 统一格式 + 好 description
import re
from datetime import datetime

def _ok(data):
    """成功结果模板"""
    return {"ok": True, "data": data}

def _err(msg):
    """失败结果模板"""
    return {"ok": False, "error": msg}

def query_taigu_kwh(taigu_id, date):
    """查询某个台区在某一天的电量（kWh）。单个台区单日数据用这个。"""

    # 武器 1：参数校验
    if not re.match(r"^T\d{2,3}$", taigu_id):
        return _err(f"taigu_id 格式错：'{taigu_id}'，应该是 T 加 2-3 位数字")
    try:
        datetime.strptime(date, "%Y-%m-%d")
    except ValueError:
        return _err(f"date 格式错：'{date}'，应该是 YYYY-MM-DD")

    try:
        # 真实业务：查 DB / 调 API / 读文件
        kwh = _query_db(taigu_id, date)
        if kwh is None:
            return _err(f"没找到 {taigu_id} 在 {date} 的数据")
        return _ok({"taigu_id": taigu_id, "date": date, "kwh": kwh})
    except Exception as e:
        return _err(f"查询失败: {type(e).__name__}: {e}")

# 工具说明书（带 4 条铁律的好 description）
TOOLS = [{
    "type": "function",
    "function": {
        "name": "query_taigu_kwh",
        "description": "查询某个台区在某一天的电量（kWh）。用于【单个台区单日】数据。返回 {taigu_id, date, kwh}。不要用于：多台区对比、线损率查询、计算百分比变化。",
        "parameters": {
            "type": "object",
            "properties": {
                "taigu_id": {"type": "string", "pattern": "^T\\d{2,3}$", "description": "台区编号，T 加数字，如 T07"},
                "date": {"type": "string", "pattern": "^\\d{4}-\\d{2}-\\d{2}$", "description": "日期 YYYY-MM-DD"}
            },
            "required": ["taigu_id", "date"]
        }
    }
}]

本课 vs 29 课：能力对比

维度29 课（能跑）30 课（能跑稳）
参数校验无，AI 传错就崩函数内 if 检查 + Schema pattern
返回格式每个工具自己定统一 {"ok": True/False, ...}
description一两句话4 条铁律：输入/输出/何时用/何时不用
AI 选错工具经常很少（description 写明反例）
AI 传错参数崩 / 静默错AI 收到错误信息自动重试
新人接手翻代码猜行为看 description 一目了然
🎯 本课核心结论：工具函数的稳定性靠三件事：校验参数（硬约束 + Schema 软约束）+ 统一返回（永远 {ok, data/error}）+ 写好 description（4 条铁律）。这是「能跑」到「能用」的关键，也是 35 课《评估与安全》的预演——评估 Agent 的时候，工具这层不稳健，评估全白搭。

本课学了什么

  • ✅ 武器 1：参数校验——函数内 if 检查 + JSON Schema pattern 双重保护
  • ✅ 武器 2：统一返回格式——永远 {"ok": True/False, "data"/"error"}
  • ✅ 武器 3：好 description——输入/输出/何时用/何时不用 4 条铁律
  • ✅ 错误信息要让 AI 能读懂——不抛异常，返回错误结构，让 AI 自己重试
  • ✅ Schema 是软约束，函数校验是硬约束——两者都不可少

🤔 小测

想让 AI 在多个工具中减少选错工具的概率，最关键应该改：

  1. 把工具函数名改得更短
  2. 在 description 里写清「何时用、何时不用」并给反例
  3. 工具数量越多越好，AI 选的可能性就多
  4. 把 description 改成英文，更专业

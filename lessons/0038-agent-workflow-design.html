🧭 Agent 工作流设计

第 0038 课 · P6 开篇 架构课 · 预计 15 分钟

🎯 本课目标：学会一个判断——任务里哪几步该让模型自己决定，哪几步应该写死成固定流程。学会这一条，你就不再是「什么都塞给 Agent」，而是会设计系统的人。这是 P6 所有内容的底层思路。

一、先分清两个词：工作流 ≠ Agent

过去几课你说「Agent」时，脑子里大概是「一个会自己调工具的循环」。但在工程实践里，这两件事被明确区分开了——这个区分来自 Anthropic 的权威文档 Building Effective Agents：

工作流 WorkflowAgent
路径谁定 你（开发者）预先在代码里定好 模型自己边做边定
控制权 代码控制流程，模型只做单点判断 模型控制流程，代码提供工具
可预测性 高，每一步都能预知 低，同样问题可能走不同路
适合什么 步骤明确、要稳定、要便宜、要审计 路径事先说不清、需要临场判断
📌 最重要的一句：你 37 课做的那个 capstone_kit 是 Agent（ReAct 循环，模型自己选工具）。但它里面有一处是 工作流——系统提示词规定「分析前必须先调 profile」。
设计 = 决定每一段用哪种。不是「越智能越好」。

二、五种经典工作流结构

Anthropic 那篇文档里归纳了五种常见的、把模型串起来的固定结构。不用背，但要认得出来——因为它们几乎覆盖了所有「看起来像 Agent」的重复性任务：

1 · 提示链 Prompt Chaining

输入 → [步骤A] → 中间产物 → [步骤B] → 输出

把任务拆成固定顺序的多步，每步的输出是下一步的输入。适合「先抽取、再翻译、再润色」这种一步做不到、但步骤明确的事。

2 · 路由 Routing

输入 → [分类判断] → 走分支1 / 分支2 / 分支3

先判断「这是哪一类问题」，再交给对应的处理方式。适合类型明确但处理方式不同的场景（如「退款咨询」走一套流程，「数据查询」走另一套）。

3 · 并行 Parallelization

输入 → [任务1] + [任务2] + [任务3] → 汇总

几个互不依赖的子任务同时做，最后合并；或者同一问题用几套判断并行跑，多数投票。

4 · 编排者-执行者 Orchestrator-Workers

输入 → [主模型拆任务] → [多个子任务分别做] → [主模型汇总]

由模型动态拆解任务、分派出去、再汇总。比并行更灵活——子任务数量不预设。适合「一次要改多个文件」「一次分析多个维度」这种。

5 · 评估者-优化者 Evaluator-Optimizer

[生成] → [评估] → 不合格 → 带着意见回到生成

一个模型产出，另一个（或同一模型换角色）按标准挑错，循环到达标。这跟你 34 课做的 verify 核验卡口是同一个思想——只不过你核的是数字，它核的是文本。

💡 认出来了：第 5 种就是你已经在用的东西。所以这些结构你并不陌生，只是现在有了名字，可以主动选而不是碰巧用到。

三、判断规则：哪一步该写死，哪一步该放手

这张表是本课最该记住的东西。拆任务时，把每一步过一遍：

这一步的特征该用理由
步骤固定、顺序不会变 工作流（写死） 代码做更稳、更快、更便宜，出问题能精确定位
需要临场判断、路径说不清 Agent（放手） 写死的分支覆盖不全会漏情况
结果要拿去做审计 / 要能复现 工作流（写死） Agent 同一问题走不同路，无法保证一致性
要批量跑、成本敏感 工作流（写死） 每一步的调用次数可预算，Agent 的循环次数不可控
是把多个已知步骤拼起来 工作流（提示链） 不需要「自主」，只需要「串起来」
⚠️ 最常见的过度设计：用 Agent 干工作流的活。
比如「每天把 Excel 读进来 → 算 5 个指标 → 填模板 → 发出去」——这是个固定流程，第 15 课那个定时脚本就是正解。硬做成 Agent，结果是：每次跑法不一样、出错了难排查、token 花几倍、还要担心它今天心情不好。
能用代码写死的，别交给模型决定。

四、拆任务：给每一步贴标签

拿到一个业务需求（P6 会给你电商场景的），不要一上来就写代码。先在纸上做这件事：

  1. 把流程按「人原来怎么干的」写成步骤。不要美化，就写现状。
  2. 给每一步贴标签：[确定] 还是 [需判断]。
    • [确定]：读文件、算 sum、查去重数、画图、写文件——代码能做，且答案唯一。
    • [需判断]：这句业务问题对应哪个指标、这个异常值要不要剔除、该用哪个口径——需要语义理解。
  3. 各归各位：[确定] 的步骤做成工具函数；[需判断] 的步骤交给模型。两者用「工具调用」连接——这就是 27-30 课学的接口。
  4. 标出核验点：哪一步的输出数字会被写进结论？那一步后面必须挂 verify。
📌 一个反直觉的结论：标签贴完之后你会发现，「需判断」的步骤往往只有 1-2 个——通常是「听懂问题」和「组织结论」。中间一大段都是 [确定]。
这意味着：你的 Agent 大部分代码应该是普通 Python，模型只在关键处出手。这就是 09-02 我们讨论出的那句——「便宜模型 + 好架构 > 强模型 + 裸奔」。

五、控制上下文：别把中间产物一遍遍塞回去

ReAct 循环有个天然的坑：每一步的结果都追加进 messages，步数一多，上下文越滚越大，最后模型被淹在自己制造的垃圾里。

两个做法（你 37 课项目里已经各用了一半）：

  • 中间产物落盘：大块结果（整个计算结果、生成的图表路径）写进文件，对话里只留「已存到 runs/xxx.json」这一句。capstone_kit/agent/core.py 的 save_trace 就是这个思路。
  • 画像代替全量数据：模型不该看见 10000 行数据，只该看见「行数/列/类型/取值/前 3 行」这张卡片。tools.profile 就是这个思路——34 课你亲手做的。
🎯 本课核心结论：Agent 设计不是「让 AI 包办一切」，是划一条线——线的一边用代码写死（确定性、可复现、便宜），另一边交给模型（语义判断）。会划线的人，才算会做 Agent。

六、动手任务（15 分钟，不用写新代码）

  1. 打开你 37 课的项目，写出它的完整流程步骤（大约 5-7 步）。
  2. 给每一步贴 [确定] / [需判断] 标签。
  3. 数一数：几个 [需判断]？如果超过 3 个，说明你把它当「万能助手」设计了，试着把其中几个改成固定流程。
  4. 找出核验点：哪一步的数字会被写进最终结论？verify 挂上了吗？

本课学了什么

  • ✅ 工作流 vs Agent：路径由你定（工作流）还是由模型定（Agent）——这是根本区别
  • ✅ 五种工作流结构：提示链 / 路由 / 并行 / 编排者-执行者 / 评估者-优化者
  • ✅ 判断规则：步骤固定、要审计、成本敏感 → 写死；路径说不清 → 放手
  • ✅ 拆任务方法：逐步贴 [确定] / [需判断] 标签，各归各位
  • ✅ 上下文控制：中间产物落盘、画像代替全量数据

🤔 小测

你要做一个「每周一自动生成上周销售周报」的工具：读上周数据 → 算 6 个固定指标 → 按模板生成报告 → 发到群里。用什么方式实现最合适？

  1. 搭一个 ReAct Agent，让它自己决定每周该做哪些分析
  2. 写固定流程的脚本，需要判断的地方单独调用一次模型
  3. 用多个 Agent 并行，每个负责一两个指标的独立计算
  4. 把整个任务交给一次模型调用，让它一次性完成全部工作

小测答案：B。固定流程的脚本 + 需要判断的地方单独调模型——步骤（读数据、算 6 个指标、套模板）全都固定且答案唯一，用代码写死最稳最省；只有「组织一段人读的结论文字」需要语义判断，那一步单独调一次模型。
A 错：指标是固定的 6 个，「让它自己决定做哪些分析」等于把确定性步骤变成不确定——这周算了 6 个、下周算了 4 个，没人能保证周报口径一致。
C 错：6 个指标都是在对同一份数据做不同聚合，毫秒级的计算，拆成多个 Agent 并行只是把简单问题复杂化，还多花几倍调用费。
D 错：一次性交给模型，等于让它同时负责算数（它算不准，尤其多步聚合）和写结论。数字必须由代码算，模型只负责解释数字——这是 19 课和 34 课反复强调的那条线。

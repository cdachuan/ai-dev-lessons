二、三层防御：工具层 → Agent 层 → 人兜底

容错不是在某一个地方做，而是每一层都有自己的防线：

第一层：工具层（代码兜底）

工具函数自己处理最常见的异常，不让错误传到 Agent 层。

# 39 课的 calc_gmv 已经做了输入校验——这就是第一层
def calc_gmv(df, exclude_returns=True, group_by=None):
    if "Quantity" not in df.columns or "UnitPrice" not in df.columns:
        return {"error": "数据缺少 Quantity 或 UnitPrice 列"}
    # ... 正常计算

再加一个数据清洗工具，处理真实世界最常见的坑：

# ecommerce_toolkit/cleaners.py
def clean_ecommerce_data(df):
    """清洗电商数据，返回 (clean_df, report)。
    report 记录了每一步处理了什么，供 Agent 和人核验。
    """
    report = {"原始行数": len(df)}
    work = df.copy()

    # 1. 列名标准化：去空格、统一大写
    work.columns = work.columns.str.strip()

    # 2. CustomerID 缺失 → 标记但不删（让调用者决定）
    work["CustomerID_missing"] = work["CustomerID"].isna()
    report["CustomerID缺失数"] = int(work["CustomerID_missing"].sum())

    # 3. Quantity 异常：负数 = 退货，标记
    work["is_return"] = work["InvoiceNo"].astype(str).str.startswith("C")
    report["退货单数"] = int(work["is_return"].sum())

    # 4. UnitPrice = 0 → 免费赠品，标记
    work["is_free"] = work["UnitPrice"] == 0
    report["免费赠品行数"] = int(work["is_free"].sum())

    # 5. Description 缺失 → 填"未知商品"
    work["Description"] = work["Description"].fillna("未知商品")

    report["清洗后行数"] = len(work)
    return work, report

第二层：Agent 层（重试 + 降级）

工具层处理不了的错误（如 API 超时），由 Agent 层的重试逻辑兜底。

# 29 课学的 HTTP API 工具，加上重试护栏
import time, requests

def call_api_with_retry(url, params=None, max_retries=3, timeout=10):
    """调 API，自带超时 + 重试 + 指数退避。
    用途：Agent 调外部数据源时的统一入口。
    返回：{ok: True, data: ...} 或 {ok: False, error: ...}。
    """
    last_error = None
    for attempt in range(max_retries):
        try:
            resp = requests.get(url, params=params, timeout=timeout)
            resp.raise_for_status()
            return {"ok": True, "data": resp.json()}
        except requests.exceptions.Timeout:
            last_error = "超时"
        except requests.exceptions.HTTPError as e:
            if e.response.status_code == 429:
                last_error = "限流"
                time.sleep(2 ** attempt)   # 指数退避：1s, 2s, 4s
                continue
            last_error = f"HTTP {e.response.status_code}"
        except Exception as e:
            last_error = str(e)
    return {"ok": False, "error": f"重试{max_retries}次后失败: {last_error}"}

第三层：人兜底（日志 + 告警）

前两层都挡不住的问题，要记录下来让人知道——不能静默失败。

# 工具层返回的 report / error 信息要能被看到
result = calc_gmv(df)
if "error" in result:
    print(f"⚠️ 工具返回错误: {result['error']}")
    # Agent 应该把这个错误告诉用户，而不是假装算出了结果
📌 三层防御的核心思想：工具层处理能预见的异常（字段缺失、类型错误）；Agent 层处理运行时异常（超时、重试）；人兜底处理未知异常（日志+告警）。任何一层都不该假设"数据一定是好的"或"接口一定是通的"。

三、用本数据集练容错

UCI Online Retail 数据集自带两个经典脏数据场景：

场景 1：退货单（InvoiceNo 以 C 开头）

# 退货单的 Quantity 是负数——不处理会怎样？
# 如果 Agent 不知道这个规则，直接算 GMV：
df["Revenue"] = df["Quantity"] * df["UnitPrice"]
gmv_wrong = df["Revenue"].sum()   # 被退货拉低了 ~45万

# 容错做法：工具层自动识别并标记退货
df["is_return"] = df["InvoiceNo"].astype(str).str.startswith("C")
# Agent 调工具时可以选择是否排除退货——口径透明

场景 2：CustomerID 缺失（约 25%）

# 如果 Agent 不处理缺失值直接算复购率：
orders_per = df.groupby("CustomerID")["InvoiceNo"].nunique()
# 报错：CustomerID 有 NaN，groupby 会把 NaN 当成一个分组

# 容错做法：先 dropna 再分析，report 里记录了多少行被跳过
valid = df.dropna(subset=["CustomerID"])
skipped = len(df) - len(valid)
print(f"跳过 {skipped} 行（CustomerID 缺失），占比 {skipped/len(df):.1%}")
💡 容错的最高境界：不是"遇到错误就报错"，而是优雅地处理 + 告诉用户发生了什么。比如 CustomerID 缺失时，不是简单地 dropna()，而是"跳过了 135080 行（占比 24.9%），这些行无法关联到具体客户，复购率计算基于剩余 75.1% 的有效数据"。

四、给 Agent 加一个失败重试护栏

把重试逻辑封装成一个通用护栏装饰器，任何工具函数都可以套用：

# ecommerce_toolkit/resilience.py
import time, functools

def retry_on_failure(max_retries=3, delay=1, backoff=2):
    """装饰器：工具函数失败时自动重试，指数退避。
    用法：@retry_on_failure() 加在任何工具函数上。
    """
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last_err = None
            for i in range(max_retries):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    last_err = e
                    if i < max_retries - 1:
                        time.sleep(delay * (backoff ** i))
            return {"error": f"重试{max_retries}次后失败", "最后错误": str(last_err)}
        return wrapper
    return decorator

# 使用示例
@retry_on_failure(max_retries=3, delay=1)
def fetch_exchange_rate(currency):
    """从外部 API 获取汇率——可能超时、可能限流。"""
    import requests
    resp = requests.get(f"https://api.exchangerate-api.com/v4/latest/{currency}", timeout=10)
    resp.raise_for_status()
    return resp.json()

🎯 任务（15 分钟）：选一个你 39 课写的工具函数（如 calc_gmv），给它加上重试护栏。具体步骤：
  1. 把 retry_on_failure 装饰器复制到你的工具文件
  2. 在 calc_gmv 上加 @retry_on_failure(max_retries=2)
  3. 模拟失败场景：在函数里加一行 if some_condition: raise ConnectionError("模拟网络错误")
  4. 测试：第一次调用抛异常，第二次自动重试成功
  5. 观察重试日志（你可以在装饰器里加 print(f"第{i+1}次尝试...")）

进阶挑战：如果重试 3 次都失败了，让 Agent 自动降级——比如从"精确计算"降为"用缓存的上次结果"，并在结论里标注"本次数据可能不是最新的"。

🤔 小测

你的 Agent 调用一个外部 API 获取实时汇率，第一次超时了。正确的做法是什么？

  1. 立即重试 3 次，每次都一样超时
  2. 第一次超时后等 1 秒再重试，如果还超时等 2 秒再试，3 次都失败则返回错误信息
  3. 超时就超时了，返回一个硬编码的默认汇率
  4. 把超时异常吞掉，假装没发生过
点击展开答案与解析
答案：B。指数退避重试（等 1s → 2s → 4s）是处理瞬时故障的标准做法——可能只是网络抖动，重试几次就好了。A 错：不等待直接重试大概率还是超时（对方服务器还没缓过来），还可能加重对方负担。C 错：硬编码汇率是数据造假——错误的实时数据比没有数据更危险；如果要用缓存值，必须在结论里标注"使用了缓存数据，非实时"。D 错：吞掉异常 = Agent 假装成功了但给了错误结果，这是最危险的行为。

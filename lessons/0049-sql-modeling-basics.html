🏗️ 数据建模与查询性能入门

第 0049 课 · 选修线一 SQL与查询工程 · 延伸 · 预计 20 分钟

🎯 本课目标：看懂公司数仓的「星级模型」「宽表」「汇总表」这些词，理解为什么表要那样组织，以及用你自己的数据实测一次「汇总表到底快多少」。不教你建数仓，教你会读会用。

一、两种表的角色：事实表与维度表

事实表 Fact维度表 Dimension
装什么一行=一次事件（一单/一detail行）一行=一个对象（一个客户/一个商品）
特征行数巨大、不断追加行数少、偶尔变化
你的数据里54万行订单明细38个国家、4371个客户

「星型模型」= 一张事实表在中心，若干维度表环绕，靠 key 相连，画出来像星星。为什么这样设计？事件不断追加（事实）而属性很少变（维度），分开存才不冗余。

二、为什么「宽表/汇总表」查询快：实测

你的数据上做过一个真实验：54 万行明细聚合 vs 预聚合好的 298 行汇总表，算各国 GMV：

明细表（541,909行）汇总表（298行）
建表—CREATE TABLE sales_agg AS SELECT 月,国家,SUM(gmv),COUNT(订单) GROUP BY 1,2
「各国GMV」查询耗时83.3 ms< 0.1 ms
结果Top3 完全一致：UK 6,767,873.39 / 荷兰 284,661.54 / EIRE 250,285.22
📌 一句话原理：查询成本 ≈ 扫描行数。汇总表把「反复扫 54 万行」变成「扫 298 行」，用一次预计算的存储换无数次查询的时间。真实数仓里这个差距是分钟级 vs 毫秒级。

两个注意事项（都实测过）：

  • 浮点比对要 ROUND：明细 SUM 和汇总 SUM 的浮点误差可能让「直接 == 判断」翻车，比数字先 round。
  • 汇总表有损：只能答「预聚合维度内」的问题。想按商品再拆？明细表还得在。

三、索引直觉：为什么不用讲深

索引 = 给表加一本「目录」，按 key 找行从「翻整本书」变成「查目录」。但你的场景里它排第二位：分析型查询（GROUP BY 全表聚合）主要靠扫描和预聚合，索引对 OLAP 帮助有限；它救的是「按 key 点查」的 OLTP 场景。面试能说清这句话就够了：

OLTP（业务系统）在乎单行快 —— 索引是主角；OLAP（分析）在乎全表聚合快 —— 预聚合/列存是主角。数分岗daily面对的是 OLAP。

四、你会在入职第一周遇到的东西（速查）

黑话人话
ODS / DWD / DWS / ADS贴源层→明细层→汇总层→应用层，越往后越「宽」越「聚合」
宽表把常用维度冗余进一张大表，换查询方便
拉链表记录属性每次变化的表（客户地址改了留历史）
T+1数据每天凌晨跑批，今天看到的是昨天的
数据倾斜某个 key 数据量畸大，group by 时它一个组拖慢全局

动手任务（20 分钟）

  1. 照课文在你的数据上建 sales_agg 汇总表，复现 83ms → <0.1ms 的对比。
  2. 用 ROUND 后比对两种路径的各国 GMV，确认一致。
  3. 提一个汇总表答不了的问题（如「荷兰 Top3 商品」），体会「有损」的含义。
  4. 设计：如果要每天看「新客 vs 老客」的 GMV，你的汇总表该长什么样（哪些列）？
🎯 本课核心结论：建模的本质是预先安排好「数据最常被怎么问」：事实/维度分离管不冗余，预汇总管查询快，宽表管取数方便。你入职不用建数仓，但要看得懂别人为什么这样建，以及知道手里的表适合答什么问题。

本课学了什么

  • ✅ 事实表 vs 维度表：事件大而追加，对象少而稳定，分开存
  • ✅ 预汇总的威力：54万行 83ms → 298行 0.1ms，存储换时间
  • ✅ 汇总表有损：只能答预聚合维度内的问题，明细必须保留
  • ✅ OLTP/OLAP 分野：索引救点查，预聚合救聚合
  • ✅ 数仓黑话速查：ODS/DWD/DWS/ADS、宽表、拉链表、T+1

🤔 小测

老板要「实时大屏：今天每小时的 GMV」，而你数仓里只有昨天之前的 T+1 明细表。最合理的说法是？

  1. 用汇总表凑一下，数字差不多就行
  2. T+1 明细表给不了「今天」的数据——需要接入实时数据源，先如实说明限制
  3. 拿昨天的数据假装是今天的
  4. 把明细表查快一点就能实时了

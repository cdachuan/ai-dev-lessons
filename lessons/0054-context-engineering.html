🧠 上下文工程：裁剪 / 压缩 / 记忆

第 0054 课 · 选修线三 Agent深水区 · 开篇 · 预计 20 分钟

🎯 本课目标：上下文窗口是 Agent 最稀缺的资源。塞什么、留什么、扔什么——这门「上下文工程」决定 Agent 是聪明还是又贵又蠢。用你数据的真实数字算一笔账开场。

一、一笔账：上下文有多贵

你的 54 万行订单数据，如果把全量塞进上下文（每行约 8 token）：≈ 4.3M tokens——任何模型的窗口都装不下，装得下也贵到荒谬。而 34 课你做的 profile 画像卡片：约 50 词，却回答了「数据长什么样」这同一个问题。

📌 核心认知：上下文不是「越多越好」的仓库，是每一步都要付费的工作内存。模型只能看见窗口里的东西——塞噪音，它就被噪音带偏；裁剪得当，它又快又准。

二、裁剪：什么值得留在窗口里

留扔
系统提示（角色+规则+口径）完整历史对话（多轮后只留摘要）
当前任务相关的问题与约束工具返回的大块原始数据
数据画像/摘要卡片已确认无误的中间计算过程
最近 2-3 轮关键交互试错过程中的失败输出

你的 insight_agent_mvp 已经在这么做了：profile 返回画像而非数据、verify 只返回结论而非全部中间值、每次提问的 trace 落盘而不回灌——回头看，34 课你已经在做上下文工程了。

三、压缩：三招处理「必须保留但要变小」

1 · 摘要压缩

30轮对话 → [LLM摘要成5句话] → 继续对话

长会话定期把历史压成「任务目标+已做决定+当前状态」。摘要本身一次调用成本，换后续每轮都变小的窗口。

2 · 结构化提炼

工具大结果 → [代码抽关键字段] → 只留JSON卡片

用代码（不花模型钱）从工具输出里抽需要的字段。查询结果 1000 行？抽成「行数+Top5+异常标记」。

3 · 外置记忆（落盘）

不常用但会用到 → [写文件] → 需要时按需读回

你的 runs/ 留痕就是外置记忆：不占窗口，随时可查。窗口是工作台，文件系统是仓库。

四、多步任务的上下文预算

ReAct 每一步都把「全部历史+工具结果」重新发一遍——步数越多，窗口涨得越快。实用的预算习惯：

  • 设步数上限（你的 MVP 是 10 步），逼近上限时触发「总结+重启会话」策略
  • 工具返回设大小上限：超过 N 行自动截断+提示「结果已截断，请缩小范围」
  • 分阶段重开：大任务拆成几个阶段，每阶段新会话只带上一阶段摘要

动手任务（20 分钟）

  1. 算一笔账：你的 MVP 跑满 10 步、每步窗口膨胀 2000 tokens，总成本多少？画像卡片方案省多少？
  2. 给 sql_query 工具（48课）的返回加截断保护：超过 100 行自动摘要。
  3. 写一个「会话摘要器」prompt：输入 30 轮历史，输出 5 句结构化摘要（目标/决定/状态）。
🎯 本课核心结论：上下文工程 = 窗口里的每一寸都要挣自己的租金。塞进来的信息必须服务当前步的决策；不服务的，压缩、外置或扔掉。Agent 的聪明一半在模型，一半在你给它看了什么。

本课学了什么

  • ✅ 窗口=付费工作内存：全量数据 4.3M tokens vs 画像 50 词
  • ✅ 裁剪清单：系统提示/画像/关键交互留，原始数据/失败尝试扔
  • ✅ 压缩三招：摘要、结构化提炼（代码不花钱）、外置落盘
  • ✅ 步数预算：上限+截断+分阶段重开

🤔 小测

Agent 连续对话 40 轮后明显变笨、回答开始跑偏，最可能的原因和首选解法？

  1. 模型变笨了，换个更强的模型
  2. 窗口里堆满历史噪音稀释了关键指令——压缩/裁剪历史，保住系统提示和当前任务状态
  3. 把系统提示再加长 3 倍
  4. temperature 调高点

（答案见底部）

← 上一课：因果入门 下一课：成本与延迟控制 → 📖 术语表

小测答案：B。40 轮历史 + 各步工具输出把「关键指令」稀释成大海里的一滴水——模型注意力被噪音淹没（lost in the middle）。压缩历史、保住系统提示和任务状态，窗口立刻「变聪明」。
A 错：换模型最贵，且治标不治本——再强的模型也会被噪音淹没。
C 错：火上浇油，窗口更挤，关键信息被稀释得更厉害。
D 错：temperature 管随机性，不管注意力分配。先修上下文，再谈换模型。

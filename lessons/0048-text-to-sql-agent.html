🤖 Text-to-SQL Agent：让 LLM 写 SQL，你来验

第 0048 课 · 选修线一 SQL与查询工程 · 收官 · 预计 25 分钟

🎯 本课目标：把 46-47 课的 SQL 能力和 34/43 课的 verify 思想合体，做出「数据智能体岗」JD 里最热的一个技能点：用户说人话 → LLM 生成 SQL → 引擎执行 → 独立路径复算校验 → 才给结论。你的求职作品从此多一个杀手级模块。

一、为什么 Text-to-SQL 必须配 verify

LLM 写 SQL 的水平参差：语法错误是小事（引擎会报错），语法对但口径错是大事——它不知道你们家「客单价」分母含不含退货单。直接把 LLM 的 SQL 结果端给老板，等于把 34 课拦截过的「模型算错数」换了个入口又放进来。

⚠️ 铁律：Text-to-SQL 的产出永远经过两道关：①只读防护（引擎只许 SELECT）；②verify 独立复算（同一问题用 pandas 另算一遍，两边一致才出口）。少一道，就退回「裸奔 LLM」。

二、架构：四段流水线

Text-to-SQL 流水线

用户问题 → [①schema感知] → [②LLM生成SQL] → [③duckdb只读执行] → [④pandas独立复算verify] → 结论

①②是模型/提示的活，③④是代码写死的活——38 课「划线」思想的标准应用：确定的步骤写死，只有生成 SQL 一步交给模型。

2.1 schema 感知：先让模型「看见」表结构

LLM 不在你机器上，它不知道你的列名。生成 SQL 前必须把 schema 塞进 prompt：

SCHEMA = """表 df，54万行电商订单：
  InvoiceNo(发票号,C开头=退货), StockCode, Description, Quantity(负=退货),
  InvoiceDate, UnitPrice, CustomerID(25%缺失), Country
  业务口径: 客单价=净GMV/有购买行为的发票数; 退货记负收入不删行"""
📌 口径写进 schema：注意最后一句——把你的口径字典（见 lessons/code/metric_guard）里的关键口径直接喂给模型。prompt 里写口径，比事后发现算错便宜一百倍。

2.2 生成：带约束的 prompt

prompt = f"""你是一个 SQL 生成器。根据表结构与口径，把用户问题转成一条 duckdb SQL。
要求:
1. 只生成 SELECT 语句，禁止任何修改数据的操作
2. 在注释里标注你用了口径字典的哪一条
3. 输出后预估: 结果大概几行、什么量级（供人工/程序核验）

表结构与口径:
{SCHEMA}

用户问题: {question}"""

第 3 条是故意的：让模型自己报「预期形态」，你就可以写断言——结果 10000 行 vs 预期「约5行」当场暴露。

2.3 执行：只读防护写死在代码层

import duckdb, re
def safe_execute(sql: str, conn) -> "pd.DataFrame | None":
    s = sql.strip().rstrip(';').lower()
    if not s.startswith('select') and not s.startswith('with'):
        return None                        # 拒绝非查询
    if re.search(r'(insert|update|delete|drop|create|alter)', s):
        return None                        # 双保险：关键词黑名单
    try:
        return conn.execute(sql).fetchdf()
    except Exception as e:
        return None                        # 执行失败≠答案，交回上层

2.4 verify：pandas 独立复算

同一个问题，让模型额外生成一段等价的 pandas 代码（或固定走你的工具箱），两边数字逐位比对。真实双路径实验（本课在你数据上实跑）：

-- LLM 生成的 SQL（五国 GMV，排除英国本土）
SELECT Country, ROUND(SUM(Quantity*UnitPrice),2) AS gmv,
       COUNT(DISTINCT InvoiceNo) AS orders
FROM df
WHERE CustomerID IS NOT NULL AND UnitPrice > 0 AND Country != 'United Kingdom'
GROUP BY Country ORDER BY gmv DESC LIMIT 5

🎯 本课核心结论：Text-to-SQL 的价值不在「LLM 会写 SQL」，在工程化围栏：schema+口径喂饱、只读防护、双路径 verify、评估集回归。这四样做齐，你面试讲这个模块时，讲的是「我如何保证 AI 算的数可信」——这正是数据岗和 AI 岗都想要的人。

LLM 生成的 SQL 语法正确、跑出了结果，但忘记排除退货单（Quantity<0 的行被 SUM 进了 GMV）。哪道防线本来能拦住它？

小测答案：B。语法对、口径错——只有独立实现路径的复算能抓住：pandas 版按正确口径算出不同的数，两边对不上，差异暴露口径问题。
A 错：只读防的是「改数据」，防不了「读数读错口径」。
C 错：temperature=0 只减少随机性，模型对口径的理解错不会因此消失。
D 错：更强的模型依然不知道「你们家」的口径定义——这不是智力问题是信息问题，口径必须显式喂给它（schema/口径字典）。错误能穿过语法层，但穿不过独立复算。

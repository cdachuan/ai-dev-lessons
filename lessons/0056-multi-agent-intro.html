🤖🤖 多 Agent 协作入门

第 0056 课 · 选修线三 Agent深水区 · 预计 20 分钟

🎯 本课目标：学会两个判断——什么时候值得拆多 Agent，什么时候单 Agent 更好；以及最实用的多 Agent 结构：编排者-执行者（38 课五种结构里的第 4 种）落地。

一、先泼冷水：多数场景不需要多 Agent

单 Agent（你的 MVP）= 一个循环 + 一组工具，简单可控。上多 Agent 的正当理由只有三个：

  • 上下文隔离：子任务的中间过程又臭又长（如爬网页），不想污染主 Agent 的窗口（54 课）
  • 并行加速：子任务互相独立且耗时（如同时分析 5 个国家）
  • 专业分化：不同子任务需要差别巨大的工具集或提示（如「读代码的」和「写报告的」）

除此之外的「多 Agent」多半是把简单问题复杂化：调试难度翻倍、token 成本翻倍、错误传递链变长。先用单 Agent + 好工具做到极限，再谈拆分。

二、编排者-执行者：最实用的落地结构

Orchestrator-Workers

用户任务 → [编排者:拆解+分发] → [执行者A][执行者B][执行者C 并行] → [编排者:汇总校验] → 结论

编排者自己也可以只是代码：拆解规则固定时（如「5 个国家各出一份分析」）根本不需要 LLM 编排——38 课说的「能写死的写死」。

接到你的 MVP 上，一个真实可做的改造：「五国对比报告」任务——

  1. 编排者（代码）把任务拆成 5 个独立子任务：每个国家一份「KPI+趋势+RFM」
  2. 5 个执行者（同一个小模型，带不同参数）并行跑，各自只看自己国家的数据切片——上下文天然隔离
  3. 汇总者（代码）拼接结果；verify 层（42 课）对 5 份结果的合计数与全量复算比对——拆了并行，数还要对得上

三、多 Agent 的三条纪律

  1. 接口契约先行：每个执行者的输入输出写成结构化 schema（像你的工具返回 {"ok":bool,...}），编排者只依赖契约不依赖「它大概会返回什么」
  2. 失败隔离：一个执行者挂了不能拖垮全局——超时、重试、降级（41 课护栏在子 Agent 层照常生效）
  3. 结果必须核验：并行结果汇总是新引入的错误机会，合计数/去重数要和独立复算比对

四、什么时候值得：一张决策卡

信号决策
子任务独立、可并行、各自输出短值得拆（并行+隔离双赢）
子任务串行依赖、上下文共用多别拆，单 Agent 流水线
只是想「多个角色讨论」别拆，一次调用多角色提示更省
主任务窗口被某类脏活污染拆出去做上下文隔离

动手任务（30 分钟）

  1. 把「五国对比报告」用代码编排 + 单模型执行实现，测并行 vs 串行的总时长差。
  2. 给每个子结果加合计校验：5 国 GMV 加总 vs 全量去 UK 后复算，验证一致。
  3. 故意让一个执行者超时，验证失败隔离：其余 4 国照常出结果，坏的那份标记降级。
🎯 本课核心结论：多 Agent 是工程手段不是架构信仰：为上下文隔离、并行加速、专业分化而拆；拆了就要有契约、有隔离、有核验。「能用单 Agent + 好工具解决就别拆」——这句话在面试里说出来，比讲十个多 Agent 框架更显得懂行。

本课学了什么

  • ✅ 三个正当拆分理由：上下文隔离 / 并行加速 / 专业分化
  • ✅ 编排者-执行者：编排可以是纯代码，执行者并行+切片
  • ✅ 三条纪律：接口契约、失败隔离、结果核验
  • ✅ 决策卡：独立可并行才拆，串行依赖别拆

  3. 38 个任务串行但每步压缩上下文
